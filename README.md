# QBZ Downloader — Windows PortableApps Builder Kit b1r3

**Mode: PORTABLEAPPS only.** This is an independent, unofficial builder for [ifauzeee/QBZ-Downloader](https://github.com/ifauzeee/QBZ-Downloader). It creates a source-built Windows x64 Electron application, a genuine compiled C++ root `QBZDownloaderPortable.exe`, a ready-to-extract PortableApps ZIP, and a separate community NSIS `.paf.exe` installer built through the pinned shared action. **No installation is required to run the ZIP.** This kit is **not** a PortableApps.com-certified package.

> This ZIP contains the **builder source and GitHub workflows**, not a precompiled Windows application. The Windows EXE, application ZIP and installer are produced by GitHub Actions. A green CI run proves packaging and static checks; GUI operation and true host-state containment still require the Windows acceptance tests in `docs/WINDOWS-ACCEPTANCE.md`.

## Start here — GitHub Desktop (no local compiler)

1. Sign in at [github.com](https://github.com). Select **New repository**. Use a new name such as `QBZDownloader-PortableApps-Builder`. **Do not fork QBZ-Downloader.** Choose **Private** if you want your generated releases restricted to your account; choose Public only if you intend public distribution and license obligations are met. Create the empty repository.
2. In **GitHub Desktop**, select **File > Clone Repository**, choose your new repository, and clone it to a local folder.
3. Extract every file from this builder-kit ZIP into the clone root, including the **`.github`** folder. It must look like `.github/workflows/build.yml`, `scripts/resolve_upstream.py`, `launcher/main.cpp`, and `README.md`.
4. In GitHub Desktop, review changed files, enter a summary such as `Add QBZ Downloader PortableApps builder b1r3`, and click **Commit to main** then **Push origin**. No manual Git initialization or upstream fork required.
5. On the repository's GitHub website, select **Actions**. Enable actions when prompted. Select **QBZ Downloader - Build PortableApps ZIP and Installer**, then **Run workflow**.
6. Leave `upstream_version=latest` and `upstream_commit` empty for a tagged stable release. **Important:** the public upstream Releases page currently lists no downloadable releases, and a corresponding stable tag has not been confirmed. If the log says `NO STABLE UPSTREAM TAGS FOUND`, re-run with **allow_unreleased_snapshot=true**. This is a deliberate opt-in to a specifically recorded upstream commit, **not** a verified official stable release. Or provide an independently verified 40-character upstream SHA together with its matching package version. Never use a random SHA.
7. Leave `publish=true` to create release assets in **your builder repository**. The job obtains code, builds QBZ, prepares portable folders, compiles the launcher, tests the layout, creates the ZIP, invokes the pinned installer builder, and publishes through the pinned publisher. It does not need a Windows desktop session, local Node.js, manual downloads, elevation, or a personal access token.
8. Open the workflow run to see each step and any failure. On success, open your builder repository's **Releases** tab. Download the file ending in `.zip` for extract-and-run, or the community `.paf.exe` for an installer-style setup. Find the published `SHA256SUMS.txt` and verify hashes when transferring the files.
9. ZIP route: extract the whole `QBZDownloaderPortable` folder to a user-writable drive or USB location. Double-click `QBZDownloaderPortable.exe` **at the root** (not the EXE inside `App`). In PortableApps Platform choose **Apps > Refresh App Icons** as needed.
10. Installer route: run the `.paf.exe` generated by the pinned custom NSIS action and install beside other PortableApps folders. It is **PortableApps-style**, not the official PortableApps.com Installer. Check installer destination and preservation in a disposable test folder before placing it alongside personal data.

## Build outputs

Expected naming is based on the actual source version and first 12 source-SHA characters, not the shared publisher version:

- ZIP: `QBZDownloaderPortable-<upstream-version>-<source-sha12>-b1r3.zip`
- Community installer: `QBZDownloaderPortable_<package-version-four-components>_custom-nsis-r3.paf.exe` (final name is supplied by the pinned package-builder action).
- Release tag: `portable-qbz-v<version>-<sha12>-b1r3`; a ZIP-only release from a failed installer ends in `-zip-only`.
- ZIP contains `Other/Source/build-identity.json`, the upstream version, exact commit, lockfile SHA-256 values, builder revision, source provenance and retained upstream MIT license.
- Shared publisher creates `SHA256SUMS.txt` in the release automatically. It publishes only validated `.zip` and `.paf.exe` assets. Default pruning is **off**.

## Critical data-safety rules

**Always use the compiled root launcher.** The app inside `App/QBZDownloader/` is a normal Electron EXE; launching it directly will not set the portable environment and can use a Windows user profile. The launcher sets `QBZ_PORTABLE_DATA_ROOT` first. The fail-closed source adapter redirects Electron `userData`, `sessionData`, logs, backend runtime, and new-profile downloads into `Data/` before application services start.

The launcher **does not automatically import** `%APPDATA%/QBZ Downloader` or delete existing installed-app data. It also does not run broad TraceGuard/ShellGuard scavenging. This is intentional: the reviewed app can accept direct redirection, and there is no established evidence that sweeping shared Windows locations would be safe. Windows shell caches may remain; see audit.

- **Upgrade:** fully exit QBZ. Make a backup of the whole `QBZDownloaderPortable` folder (especially `Data`). Extract a *new* release into a separate folder, then copy your existing `Data` directory into it **without overwriting it with default data**. Start the new root launcher. Never replace individual running `.exe` or `.node` files. Verify a track and your settings.
- **Rollback:** keep a known-good full-folder backup of the old app and its matching Data state. After a database schema migration, do **not** run an old app against the migrated Data without restoring the matching backup. Stop both versions first.
- **Relocation:** exit completely, copy/move the *whole* portable folder including Data, then start the root launcher in its new location. Review any **previously user-selected absolute download/library paths** in Settings; they are not automatically rewritten.
- **Windows account changes:** the upstream application uses Electron `safeStorage` for some credentials and an application key for others. DPAPI-protected values may not decrypt on a different Windows account/PC. Back up Data securely and expect to re-enter credentials if encryption is machine/user-bound. Never disable OS encryption to force account mobility.
- **Installed-app coexistence:** the portable build uses a distinct AUMID and private profile. Do not deliberately configure the installed and portable apps to share the same backend database. Existing installed-app files and shortcuts remain untouched.
- **Download destination:** a freshly created portable profile defaults to `Data/Downloads`; an already saved custom absolute path can remain external. This kit does not copy or delete personal music files.

## How to retry a failed installer without rebuilding QBZ

A successful ZIP validation can be followed by a failed installer action. In that case, the workflow attempts to publish a separate **ZIP-only** release and finishes as failed to make the installer problem visible. Once you have that ZIP-only release:

1. Select **QBZ Downloader - Package Installer from Validated Release ZIP** in Actions.
2. Enter the exact earlier `portable-qbz-...-zip-only` release tag.
3. This workflow verifies the release's publisher-managed marker and published checksum, safely extracts the previously validated ZIP, and runs only the pinned shared installer action.
4. On success, it publishes the verified ZIP and new `.paf.exe` under a `...-pack-r3` tag. No upstream recompilation is performed.

## Verified integration boundaries

- `vhick/Portable-Package-Builder@v1.0.0` — validated its `action.yml` interface: `source-dir`, `output-dir`, `engine=custom-nsis`, Windows-backslash `running-exe`, `timeout-seconds`, and `package-revision`, with outputs `installer-file` / SHA256 / app identity / version.
- `vhick/portable-release-publisher@v1.1.1` — inspected `action.yml` and `scripts/publish.py`. Uses `files`, `tag`, `release-title`, `tag-prefix`, `keep-releases=3`, `prune=false`, and explicit dry-run then publish. It creates SHA256SUMS and refuses to silently modify foreign releases.
- The workflow uses the specified **pinned tags** because the exact immutable action commit SHAs were not independently verified here. Before moving to production release pipelines, resolve and audit immutable action SHAs.
- Both workflows run on hosted Windows runners. `build.yml` is manual only. Only `contents: write` is requested; no elevated Windows access, extra PAT, background install or external private tooling.

## b1r3 fix (uploaded CI log `115934299115`)

The b1r2 build compiled React, TypeScript and packaged Electron but failed on a
now-obsolete hardcoded SQLite native addon location. `better-sqlite3` v13.0.3
ships `prebuilds/win32-x64.node` and its `lib/binding.js` prefers this path.
The b1r3 builder dynamically validates this v13+ loader layout, retains a
checksum-verified module snapshot **before** electron-builder, restores only
that module if the packager omits it, and tests a real SQLite query using the
packaged Electron runtime before publishing. Older SQLite module versions
retain the `build/Release/` path. Changes have been locally regression-tested,
not Windows-compiled in this environment.
